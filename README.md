# Avito Test Assignment – PR Reviewer Service

Сервис автоматически назначает ревьюеров для pull request’ов внутри команды и предоставляет HTTP API для управления командами, пользователями и просмотром статистики. Ниже — краткая инструкция по запуску приложения и тестов.

## Требования

- Go 1.25
- Docker + Docker Compose v2
- GNU Make

## Подготовка окружения

1. Скопируйте пример окружения и при необходимости скорректируйте значения:
   ```bash
   cp .env.example .env
   ```
2. Убедитесь, что переменные `DB_*` и `HTTP_PORT` совпадают с ожидаемыми портами/логинами. По умолчанию приложение будет доступно на `http://localhost:8080`.

## Запуск приложения

```
make run          # docker compose up --build -d
make logs         # логи приложения
make stop         # docker compose down (не удаляет volumes)
make stopv        # docker compose down -v --remove-orphans (удаляет volumes)
```

Миграции применяются автоматически контейнером `migrator`. 

После успешного запуска HTTP API доступен на порту `HTTP_PORT` из `.env`.

Также запустить приложение можно просто через
```bash
docker-compose up
```

## Docker-окружение для тестов

Интеграционные тесты используют отдельную БД, описанную в `docker-compose.test.yml`.

```
make test-env-up     # поднять postgres_test
make test-env-down   # остановить и удалить тестовый контейнер
```

## Запуск тестов

Перед прогоном убедитесь, что `make test-env-up` запущен и переменные `TEST_DB_*` в `.env` совпадают с настройками тестового контейнера.

```
make test             # go test ./... -cover
make test-handlers    # только HTTP-хэндлеры
make test-repositories# только слой репозиториев
```

Дополнительно:

- `make fmt` — `go fmt ./...`
- `make lint` — `golangci-lint run ./...`

Оставил некоторые issues линтера, которые посчитал минорными/некорректными в контексте задания. 
По этой же причине в коде в некоторых местах есть заглушки линтера, посчитал жалобы линтера не совсем корректными в этих местах (например тесты).

## Описание/допущения/комментарии

Работа выполнена в соответствии с предоставленным контрактом api, дополняя его некоторыми ошибками.
Также в api добавлены enpoints статистики (доп задание), предоставляющие небольшой статистический набор по количеству назначений пользователя ревьюером, как для всех PR, так и только для OPENED

Полный контракт можно увидеть в 

```
api/docs/openapi.yml
```

Также выполнено доп задание реализации интеграционных тестов. 
Исходя из рекомендаций по заданиям прошлых лет, тестирование выполнено так:
* service layer - unit-тестирование с mock
* repositories и handlers - интеграционное тестирование

Ознакомиться со структурой (схемой) БД можно [в этой диаграмме](https://dbdiagram.io/d/avito-test-assignment-6922e8c6228c5bbc1a16bb26)

Исходя из рекомендаций прошлых лет решил вынести статусы PR в отдельную таблицу, не создавая enum-ов и тп.
При старте сервиса статусы подтягиваются из БД в необходимый маппер (предполагается, что добавление нового статуса - новая миграция + перезапуск сервиса, либо можно сделать фоновую рутину, которая с некоторой периодичностью подтягивает статусы из таблицы)

Размышлял над хранением id User и PR, можно было бы сделать в формате uuid/auto-increment serial, но решил оставить как в контракте - так как id приходят нам из какого-то внешнего сервиса, мы их не создаем.
Это снижает скорость работы БД, но в случае реализации с храненеим двух id (internal БД и external пришедший в сервис) - получили бы накладные расходы на дополнительные JOIN, также замедляющие работу(скорее всего даже больше).
ID валидируются на этапе попадания в api-layer кастомными валидаторами, реализованными в: 
```
pkg/validators
```

UserID строго в формате u"число" (u1, u2, u123)
PR_ID строго в формате pr-"число" (pr-1, pr-123)

Валидация входных данных проводится на уровне api-layer, также есть небольшая валидация на уровне domain-layer, но она не затрагивает обработку входных данных, она нужна только для поддерживания консистентного состояния модели и ее неанемичности.
Такой выбор сделан по рекомендации о "едином источнике истины".

Некоторые методы(multi-write) service-layer выполнены в транзакциях, для этого в репозиториях есть pgxTm.CtxGetter. 
Ознакомившись с рекомендациями прошлых лет и с кодом данного пакета в качестве менеджера транзакций решил воспользоваться:
```
github.com/avito-tech/go-transaction-manager/drivers/pgxv5/v2
github.com/avito-tech/go-transaction-manager/trm/v2/manager
```

Снова исходя из рекомендаций и прошлого опыта написания проектов в качестве sql-builder в репозиториях используется:
```
github.com/doug-martin/goqu
```

PullRequestRepository работает с двумя сущностями (pullRequest и prReviewer), как с единым аггрегатом.

Все репозитории работают исключительно с данными, не выполняя бизнес-логики.

Ошибки реализованы в обертке, что дает единый источник истины ошибок, их код и их удобный маппинг

```
internal/domain/errors
```
